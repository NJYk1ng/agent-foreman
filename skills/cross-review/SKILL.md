# 审核：对照验收标准，只报能演示的问题

你是**领导**。工人交了 `STATUS.md`，你要审。

先读 skill `agent-contract` —— 契约定义了 `REVIEW.md` 的格式。**本 skill 只讲怎么审好。**

> ⭐ **这是最花钱的一步。** 实测：一次 `codex exec` 的底价 ≈ **7.3k token**，
> 再加 diff 和上下文。所以**审之前先看值不值得审**（见第五节）。

---

## 一、审之前：先看工人有没有资格被审

打开 `.foreman/STATUS.md`，检查三件事：

| 检查 | 不合格就 |
|---|---|
| 每条 AC 都有结论（✅/❌/⏳）？ | **退回**，写 `REVIEW.md` 说"汇报不完整，无法审" |
| `[命令]` / `[观察]` 的都贴了**真实输出**，不是复述？ | **退回**，要求贴原始输出 |
| 任务状态词用了五个之一，且 `UNVERIFIED` 没被写成 `DONE`？ | **退回** |

⭐ **退回不是刁难。** 一份"每条都✅但没贴输出"的汇报，让你无法独立复现 ——
那你就只能选择"信他"或者"自己重跑一遍"，两个都比退回更贵。

---

## 二、核对验收标准：先这里，后 diff

**顺序很重要。** 先逐条核对 AC，再看 diff。理由：AC 是契约，diff 是实现。
反过来的话你会被实现细节牵着走，忘了本来要什么。

对每条 AC：

| 级别 | 你怎么核 |
|---|---|
| `[命令]` | **自己再跑一遍**。工人贴的输出可能是旧版本的 |
| `[观察]` | 自己再观察一次，对比工人贴的值 |
| `[现场]` | ⚠️ **你不能判通过**。只能判"复现步骤写没写清" |

⭐⭐ **`[现场]` 那几条，你只能写 `⏸ 无法判定`。**

不许因为"看代码应该没问题"就给它判通过 —— 你**没有**在现场，你证不了它。
工人证不了、你也证不了，那就**只有人能证**。写清楚，交给人。

### ⚠️ 但要把两种 `⏸` 分开写 —— 别让人以为他还没验

`⏸ 无法判定` 是**你对自己**的判定（"我证不了"），**不是**"需求方还没验"。
这两件事长得一样、意思完全不同，写混了会让人白跑一趟。

```markdown
❌ 需求方已经验过了，你还写这样 —— 他看了会以为你要他再去验一遍：
   - T1/AC3 `[现场]` ⏸ 无法判定 —— 由需求方现场验收

✅ 分开写清楚：
   - T1/AC3 `[现场]` ⏸ 无法判定（需求方【尚未】验证）—— 交给人去验
   - T1/AC3 `[现场]` ⏸ 领导无法独立判定 —— 需求方已于 <时间> 验过并报告通过，
                                              记录在 STATUS.md；我只记我证不了
```

**判据**：翻一眼 `STATUS.md` 里那条 `[现场]` 是 `⏳` 还是 `✅`。

| STATUS 里是 | 你写 |
|---|---|
| `⏳ 待现场验证` | `⏸ 无法判定（需求方尚未验证）` |
| `✅` + 复现记录 | `⏸ 无法判定（需求方已验，记录在 STATUS）` |

> 📌 这条是跑闭环跑出来的（2026-10-17，`pelican-bike` 第 3 轮）：
> 需求方已经断网验过、STATUS 里也记了 ✅，领导却写「AC3 按契约记为"无法判定"，**由你现场验收**」——
> **规矩没写错，措辞让人以为还要再跑一趟。** 同一件事两种读法，就是这个坑。

### ⭐ 工人贴的每一条命令，你都要自己重跑一遍

上面表格里写的「自己再跑一遍」**不止 `[命令]` 那一条**。
工人贴在 `STATUS.md` 里的**每一个命令块** —— 包括他自己加的「额外自证」——
**你都要重跑。一条都不许采信。**

**数一数，两个数必须相等：**

```
工人一共贴了几个命令块  ==  你独立跑了几条
```

对不上就是**没审完**。在 `REVIEW.md` 里写清楚哪几条没跑、为什么。

⭐ **为什么这么硬**：工人贴的输出，**你从文本上分不出它是真跑的还是凭记忆写的** ——
两者长得一模一样。**唯一的区分办法就是自己跑一遍。**

> 📌 这条是跑闭环跑出来的（2026-10-16，`pelican-bike`）：
> 工人一份 `STATUS.md` 贴了 5 项自证 / 4 个命令块，领导**只独立跑了 `test -f index.html` 一条**，
> 其余 4 条照工人说的采信了，还给 `PASS`。
> **而就在同一份 STATUS 里，工人自己招了**：AC1 那段输出他一开始是「凭印象写的」，
> 交出去之前自查才发现、才换成真输出。
> ⇒ **采信是有真实风险的，不是假想。** 那一次恰好他自己发现并改了；
> 下一次他不会每次都发现。

## 三、再看 diff：只报这一类问题

在 AC 都核对完之后，看改动本身。用这套判据 —— **全部成立才报**：

- 影响**正确性 / 安全 / 性能 / 可维护性**，且是实质的
- 是**离散的、可行动的**
- 是**本次改动引入的**（既有问题另记，不进正文）
- 能**从代码演示**出受影响的场景或调用路径
- 作者知道了**大概率会改**

### 明确不许报的

| 不许报 | 为什么 |
|---|---|
| 推测性担忧（"可能在高并发下…"） | 演示不出来 = 你的猜测，不是发现 |
| 既有问题（不是这次改的） | 混进来会让这次审没法收口 |
| 风格挑剔 | 风格不阻塞。有 lint 就让 lint 管 |
| "这段可以更优雅" | 那是意见，不是缺陷 |
| **为了凑数编一条** | ⭐ **没找到就写「无发现」。** 编一条的代价是作者花时间改一个不存在的问题 |

### 分级

| 级别 | 含义 | 阻塞吗 |
|---|---|---|
| `P0` | 发布阻断 / 严重故障 | ✅ 阻塞 |
| `P1` | 紧急缺陷，下一步就该修 | ✅ 阻塞 |
| `P2` | 普通缺陷 | ⛔ **不阻塞**，记下来 |
| `P3` | 影响低 | ⛔ **不阻塞**，记下来 |

⭐ **`P2`/`P3` 不阻塞** 是额度纪律的一部分 —— 不然每一轮审都会带出新一轮修复，
额度在收敛之前就烧光了。

## 四、⚠️ 用 `codex review` 时要知道的实测事实

如果你用命令行版的独立复核（**全新会话、没有你的上下文** —— 更接近"另一双眼睛"）：

```bash
# 审未提交的改动
codex review --uncommitted -

# 跟基线分支比
codex review --base main -

# 审某个提交
codex review --commit <sha> -
```

把验收标准**从 stdin 喂进去**（`-` 就是"读 stdin"）：

```bash
cat .foreman/PLAN.md | codex review --base main -
```

**四条实测踩到的：**

| 事实 | 后果 |
|---|---|
| ⚠️ **有 `[P1]` 发现，退出码仍是 0** | ❌ **不能靠退出码判断通过与否**，必须解析输出里的 `[P0]`/`[P1]` |
| ⚠️ **没有 `--json`** | 只能解析 markdown |
| ⚠️ **输出可能重复**（实测同一段打了两遍） | 解析器要能容忍重复和噪音 |
| ⚠️ **耗时约 30 秒**（1000 行的 commit） | 别放在会超时的管道里 |

**输出格式**（和本契约一致，不用转换）：

```
- [P1] <一句话标题> — path/to/file.py:123
  <一段话：什么场景会走到这里、为什么错>
```

**换档位**（档位会影响审核的严格度和分级 —— 同一缺陷强档报 `P1`、便宜档报 `P2`）：

```bash
codex review -c model="gpt-6-luna" --base main -
```

## 五、⭐ 值不值得审：先算一下

审之前问自己一句：**"这次改动有实质风险吗？"**

| 情况 | 怎么办 |
|---|---|
| 改了逻辑 / 并发 / 边界 / 安全 | ✅ **审** |
| 只改了文档、注释、格式 | ⛔ **别审** —— 判 `PASS` 并在 `REVIEW.md` 里说明"低风险改动，未做深度审查" |
| 工人已经卡了两轮 | ⚠️ 先看他 `BLOCKED.md`，别急着审一份半成品 |

**预算规则（建议）：每个任务最多 1 轮 review + 1 轮复验。**
第三轮之前，先问人。

## 六、写 `REVIEW.md`

```markdown
# REVIEW — <审核对象>

> 领导：<模型> · <日期> · 对象：<sha / diff 范围>

## 结论：BLOCK | PASS

### [P1] <标题> —— `path/to/file.py:123`

<什么场景会走到这里、为什么会错、作者知道了会不会改>

## 对照验收标准

- T1/AC1 `[命令]` ✅ 已独立复现
- T1/AC2 `[观察]` ✅ 输出与我独立跑的一致
- T1/AC3 `[现场]` ⏸ 无法判定（需求方尚未验证）—— 步骤已写清，交给人去验
- T1/AC4 `[现场]` ⏸ 领导无法独立判定 —— 需求方已验通过，记录在 STATUS.md
```

**结论只有两个词**：`BLOCK`（有 `P0`/`P1`）或 `PASS`（没有）。
`P2`/`P3` 照写，但**不影响结论**。

### 收尾自查

- [ ] 每条 AC 都有核对结论，`[现场]` 的是 `⏸` 不是 `✅`
- [ ] ⭐ **我独立跑的命令条数 = 工人贴的命令块数**（对不上 = 没审完）
- [ ] 每条发现都能演示（说得出什么输入会走到那里）
- [ ] 没有推测性担忧、没有既有问题、没有风格挑剔
- [ ] 没找到就写了「无发现」，没有凑数
- [ ] 结论词是 `BLOCK` 或 `PASS`
- [ ] **没有顺手改代码** —— 你是只读的，改动由工人做
