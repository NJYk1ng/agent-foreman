# 契约：两个 agent 之间唯一的接口

两个 agent **不共享会话**。它们只通过 `.foreman/` 里的文件交流。

任何一方偏离这份契约，协作就退化成靠猜 —— 而靠猜正是本契约要消灭的东西。

---

## 一、目录与写权限

```
<项目根>/.foreman/
├── PLAN.md       当前计划        —— 只能【领导】写
├── STATUS.md     工人的汇报      —— 只能【工人】写
├── BLOCKED.md    工人的求助      —— 只能【工人】写
└── REVIEW.md     领导的审核结论  —— 只能【领导】写
```

- **提交进 git**。它是审计线索，不是缓存。
- 一个 `.foreman/` 对应一个工作单元（一个 PR 的量级）。计划做完就归档到 `.foreman/archive/`。
- 工人**不许**改 `PLAN.md`；领导**不许**改 `STATUS.md`。有意见写进自己那个文件。

---

## 二、`PLAN.md`（领导写）

```markdown
# PLAN — <一句话标题>

> 领导：<会话标识> · <日期> · 来源：<需求从哪来>

## 背景与约束

（为什么做、不能碰什么。3~6 行。写清它，工人就不用来回问。）

## 任务

### T1 <标题>

- **目标**：一句话，必须能判断"达成没达成"
- **谁写**：工人 | 领导
- **依赖**：无 | T0, T2
- **验收标准**：
  - AC1 [命令] `<命令>` → <期望输出>
  - AC2 [观察] <观察什么> → <期望>
  - AC3 [现场] <谁> / <在哪> / <做什么> → <什么算通过>
- **边界**：不许改 <文件 / 行为>
```

**字段全部必填。**「边界」没有就写 `无` —— 但写 `无` 之前想一下。

### ⭐ `谁写：领导` 什么时候用

留给满足**任意一条**的子任务：

- 涉及**坐标系 / 时态 / 并发**这类"写错了测试也测不出来、现场才暴露"的地方
- 是**核心算法**，而不是围绕它的脚手架
- 领导自己**没把握**

理由：一行都不碰的领导，等于把最难的部分交给最弱的模型，而系统恰好崩在那里。

---

## 三、⭐ 验收标准：三个级别

| 级别 | 定义 | 谁来证 | 能自动吗 |
|---|---|---|---|
| **`[命令]`** | 一条命令 + 期望输出 | 工人自己跑 | ✅ |
| **`[观察]`** | 一个可观察的事实 + 怎么观察 | 工人自己跑 | ✅ 多半能 |
| **`[现场]`** | 需要人 / 实物在场 | **人** | ❌ |

```markdown
  - AC1 [命令] `pytest tests/test_nav_retry.py` → 6 passed
  - AC2 [观察] 日志在放弃时出现 `retry exhausted`，且总共只有 3 次尝试
  - AC3 [现场] 人 / 工位 / 把 A 点用障碍物占住后下发导航 → 60s 内返回失败，机器人不动
```

**四条硬规则：**

1. **必须可证伪。** ❌「导航稳定」 → ✅「连续 5 次导航到 A 点，5 次都成功」
2. **不许自我评价。** ❌「代码看起来对」「逻辑清晰」「已优化」—— 那是感想，不是验收。
3. **`[现场]` 必须写全四件事**：谁 / 在哪 / 做什么 / 什么算通过。
   ⭐ 目的是**把"现场那几秒"压到最短** —— 不是消灭不可自动化的部分，是让它尽量小。
4. **`[现场]` 工人不许判通过**（见下）。

---

## 四、`STATUS.md`（工人写）

```markdown
# STATUS — <对应 PLAN 的标题>

> 工人：<模型> · <日期> · 提交：<sha>

## T1 <标题> — 状态：DONE

- **AC1 [命令]**: ✅
  ```
  <贴真实输出，不许复述>
  ```
- **AC2 [观察]**: ✅ 实测 32.1Hz（持续 45s）
- **AC3 [现场]**: ⏳ 待现场验证 —— 容器里没有机器人
  - 复现步骤：
    1. 把机器人摆到工位起始位姿
    2. 面板 → 点【重定位】一次（**不要连点**）
    3. 看：面板显示配准成功；`rostopic hz /slam_odom` 不掉
  - 判据：单次点击即成功 = 通过
- **改动**：`nav_goto.py:120-148`、`ros_bridge.py:88`
```

### ⭐⭐ 任务状态：五个词

| 状态 | 含义 |
|---|---|
| `TODO` | 领导已规划，工人未开始 |
| `WIP` | 工人在做 |
| `BLOCKED` | 卡住，求助已写进 `BLOCKED.md` |
| `UNVERIFIED` | 可自动的 AC 全过，但还有 `[现场]` 没验 |
| `DONE` | **全部** AC 有结论**且都通过** |

> ⭐⭐ **`UNVERIFIED` ≠ `DONE`。这是本契约最重要的一条。**
>
> "报告成功但什么都没做"这类**静默失败**，就死在这一条上。
> 不许因为"我觉得没问题"把 `UNVERIFIED` 写成 `DONE`；也不许因为"现场那条肯定没问题"直接跳过。

---

## 五、`BLOCKED.md`（工人写）

```markdown
# BLOCKED — T1

- **卡在哪**：一句话
- **已试过**：（列出来）
- **需要决定的**：一个具体问题
- **相关代码 / 日志**：（最小片段）
```

⭐「**已试过**」这一节是**省额度**的关键：没有它，领导会把工人已经排除的路再建议一遍，
白白花掉一轮。

一个任务同时只能有一个活跃的 `BLOCKED.md`。解决了就删掉（结论记进 `STATUS.md`）。

---

## 六、`REVIEW.md`（领导写）

```markdown
# REVIEW — <审核对象>

> 领导：<会话标识> · <日期> · 对象：<sha / diff 范围>

## 结论：BLOCK | PASS

### [P1] <一句话标题> —— `path/to/file.py:123`

<一段话：什么样的场景会走到这里、为什么会错、作者知道了会不会改>

## 对照验收标准

- T1/AC1 `[命令]` ✅ 已独立复现
- T1/AC2 `[观察]` ✅ 输出与我独立跑的一致
- T1/AC3 `[现场]` ⏸ 无法判定 —— 步骤已写清，现场验证后回填
```

**分级**：`P0` 发布阻断 / `P1` 紧急 / `P2` 普通 / `P3` 影响低

**报告纪律：**

- **只报本次改动引入的问题**，不报既有问题。
- **每条都要能演示**：什么样的输入/操作会走到这里。演示不出来 = 推测，不许报。
- **风格挑剔不进正文。**
- **没找到就写「无发现」。不许为了凑数编一条。**
- ⭐ **`[现场]` 那几条领导不能判通过** —— 只能判"复现步骤写没写清"。

---

## 七、变更规则

**验收标准是契约。改它 = 移动靶。**

1. 改之前必须在 `PLAN.md` 里留痕：`⚠️ AC2 变更于 <日期>：<原因>`
2. 已经派发出去的任务，改了验收标准 ⇒ **该任务重新声明为未完成**。
3. 新加任务只能**追加**，不许重排既有编号（`T3` 永远是 `T3`）。

---

## 八、额度纪律

领导的额度是**硬上限**。下面三件事花钱，**必须经过人**：

| 动作 | 触发方式 |
|---|---|
| 出计划 | 人显式发起 |
| 审代码 | 人显式发起 |
| 应答阻塞 | 人显式发起 |

⭐ **工人不许自动触发这三件事中的任何一件。**

> 这不是"没做完"，是**刻意设计**：额度烧光时流程会停在任务做到一半的地方，
> 而在额度受限的场景里，一个"停下来问"的设计比一个"全自动"的设计更可靠。
