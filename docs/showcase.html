agent-foreman

让贵的模型只动脑，让便宜的模型动手。

4 个 skill 5 次提交 闭环实测跑通 Codex 侧已验证加载
它解决什么

贵的模型贵在判断力，不在打字速度

长会话的成本是平方级的 —— 每一轮都要把整个上下文重发一遍。实测一个真实会话里 cache_read 占了全部计费 token 的 99%。而订阅制套餐卡的是 额度，不是钱：额度一光，流程当场停在任务做到一半的地方。

所以正确的分工不是"谁强谁全干"，是让贵的那一方只持有小上下文。 这也正是真实工程团队的样子：一个好的技术负责人不写大部分代码，他定方向、拆任务、审结果 —— 然后把那 10% 真正难的拆成工人能自证的小步。

这个项目把那套结构装进两个 agent。

怎么运转

两个 agent 不共享会话，只共享四个文件

不做"实时聊天"，因为两个 agent 都是回合制的 —— 跑某一轮的时候它并不在监听。 所谓实时最多是"下一个回合边界"，而每一条塞进上下文的消息，都会在之后每一轮被重发一次。

所以同步点就是这四份文件。协议刻意做得很土：能 cat 出来的协议，才是能调试的协议。

契约

四个文件，各有唯一的作者

工人不许改 PLAN.md，领导不许改 STATUS.md。 有意见写进自己那份文件。

PLAN.md 只能 领导 写
  • 每个任务带 目标 / 谁写 / 依赖 / 验收标准 / 边界
  • 验收标准必须落到 [命令] / [观察] / [现场] 之一
  • 难的那 10% 必须拆成更小的、可证伪的任务；卡住两次升级
STATUS.md 只能 工人 写
  • 每条验收标准真跑一遍，贴真实输出，不许复述
  • 状态词只用五个，且 UNVERIFIED ≠ DONE
  • [现场] 那条只能写 ⏳ + 复现步骤 —— 工人证不了它
BLOCKED.md 只能 工人 写
  • 卡在哪 / 已试过什么 / 需要哪个具体决定
  • 「已试过」那一节是省额度的关键 —— 没它，领导会把排除过的路再建议一遍
REVIEW.md 只能 领导 写
  • 只报本次改动引入的、能演示的问题
  • 没找到就写「无发现」—— 不许为凑数编一条
  • [现场] 那几条领导也判不了，只能判"复现步骤写没写清"
四个 skill

装到各自该去的那一侧

两个 harness 的 skill 格式是同一套（SKILL.md + name/description）， 但实测不自动同步 —— 只放在 ~/.claude/skills/ 的 skill，Codex 看不到，反之亦然。

skill装在哪职责关键约束
agent-contract 两端都装 定义上面那份契约 —— 唯一必须两边一致的东西 正文自包含：skill 被拷到两端，读不到仓库里的 docs/
tech-lead Codex 需求 → 带验收标准的任务清单 强制可证伪的 AC；上下文要小，不许通读代码库
cross-review Codex 对照验收标准逐条核对 + 审 diff 禁止自动触发（allow_implicit_invocation: false）—— 这是最花钱的一步
execute-plan Claude Code 按 PLAN 干活 → 逐条自证 → 写 STATUS 不许把 [现场] 标成 ✅；不许自己去叫领导
实测

它第一次跑就拒绝了给自己人盖章

拿项目自己的两个提交做靶子，让 Codex 用 cross-review 审。 它按契约先查"工人的汇报够不够格被审"，然后 BLOCK 了 —— 不给代码下结论。

## T2 — 状态：DONE

- AC3 [观察]: ✅ 三处都在 —— 下面是可 grep 的引文

  $ grep -n '为什么用文件交接' docs/architecture.md
  28:## 二、⭐ 为什么用文件交接，不用实时通信

  $ grep -n '停下来问' docs/architecture.md
  94:一个"停下来问"的设计…比"全自动"的更可靠
修法不是"改个说法让它过"，是把结论换成能被 grep 到的东西。 章节指针不算证据 —— 领导要验证只能自己重读一遍，那这次汇报就白写了。
这次实测改了什么

两条契约规则，都是被真实失败逼出来的

触发它的那个失败补进契约的规则
第一次汇报写「人工通读确认，见第二节」，被 BLOCK —— 领导无法在不重读全文的前提下核对 [观察] 的证据必须能被 grep 到。章节指针不是证据
工具的初始形态把 Codex 的输出 capture 进调用方的管道，结果人只看到一个被 tail 截断的结尾 —— 而截掉的恰好是关键的 BLOCK 理由 人闸要求可见性。光"经过人"不够，动作必须打在人能实时看到的窗口里，推理摘要必须开着
数字

实测出来的，不是估的

99% 长会话里 cache_read 占的计费 token 比例 成本的大头是"把发过的上下文再发一次"
