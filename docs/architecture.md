# 设计取舍

这份文档解释**为什么这么设计**。契约的格式规范在 [`contract.md`](contract.md) —— 那份讲"是什么"，
这份讲"为什么"。

如果你不同意某个取舍，你最该先读的就是对应的那一节，因为每个决定都是**在被某个真实的失败
教过之后**才定下来的。

---

## 一、为什么是两个 harness，而不是一个

因为**壳（harness）和模型供应商是可以解耦的**。

Claude Code 的价值大半在它的壳上 —— skill、hook、子 agent、MCP、终端交互。这个壳接得上任何
Anthropic 兼容端点。于是你可以**留着壳，换掉后面的模型**。

这条之所以重要，是因为各家供应商在两个维度上并不等价：**价格**和**可用性**。

- **价格**：前沿订阅折算到 token，可能是一个便宜端点的 10~50 倍。
- **可用性**：在部分司法辖区，各家对账号条款的执行严格程度不一致。整套工作流焊死在单一
  供应商上，等于把这家供应商的可用性变成你的可用性。

**⇒ 一个壳 + 一个能换的端点，比两个都好。** 这是本项目存在的第一个理由。

---

## 二、⭐ 为什么用文件交接，不用实时通信

技术上，"两个 agent 实时聊天"是能做的：两边都有钩子，都能在回合边界注入上下文。

**我们不做，因为实时会同时伤害三件事：**

### 1. 两个 agent 都是**回合制**的，不是常驻服务

一个 agent 在跑某一轮的时候，它并不在监听。所谓"实时"最多只能是"下一个回合边界"。
物理上不存在"一方正在听"这回事。

### 2. 每一条消息都会在之后每一轮被重新发送

这是最贵的一条。API 是无状态的：每一轮都要把整个对话重发一遍。所以**塞进上下文的每一条
消息，成本不是一次，而是"之后每一轮各一次"**。

两个 agent 高频寒暄，成本涨得比产出快。

### 3. 干扰

工人干到一半被领导插话改方向 —— 这正是要避免的那种失败。

**⇒ 真实的工程团队也不随时插话。** 高效协作靠的是**明确的同步点**：站会、PR review、交接。

所以本项目的同步点是**四个文件**，而且刻意做得很土：

> **能 `cat` 出来的协议，才是能调试的协议。**

## 三、⭐ 为什么领导只写最难的 10%

一个自然的想法是："领导负责思考和审核，一行代码都不碰。"

**这是错的分工。** 真实的前辈不是不写代码 —— 是**只写最难的那 10%**。

理由：规定领导一行都不碰，等于**把最难的部分交给最弱的模型**：

- 核心算法
- 难调的并发 / 时态 bug
- 涉及坐标系、精度边界的改动

而**系统恰好崩在这些地方**。你给了领导判断力，却要求它用判断力去*描述*一件它不能亲手做
的事 —— 描述必然失真。

**⇒ 契约里因此有 `谁写：领导` 这个字段。** 它把"判断力"和"动手"重新绑在一起，而不是二选一。

## 四、⭐ 额度纪律

### 约束不是钱，是**天花板**

如果领导那侧走的是订阅，它的边际成本在额度内是 **0**。于是优化目标不是"省钱"，是
**"别把额度烧光"**。

这个区别很大：省钱只要少说话；**防烧光需要设计**。

### 为什么人闸是设计，不是妥协

契约规定：**出计划、审代码、应答阻塞 —— 这三件事必须经过人。**

看起来像"没做完的自动化"。不是。理由是：

> 额度烧光时，流程会**停在任务做到一半的地方**。

一个"停下来问"的设计，在额度受限的场景里，比一个"全自动"的设计**更可靠**。全自动的失败
模式是不可控的（你不知道它会在哪一步撞墙）；人闸的失败模式是可控的（你决定什么时候花）。

### 两个可直接用的数字

实测（`gpt-6-luna` 档，ChatGPT 免费档）：

| 动作 | 实测 |
|---|---|
| `codex exec` 一句「好的」的**底价** | **≈ 7,300 token** —— 那是系统提示词 + 工具定义的开销 |
| **一次真实的 `cross-review`** | **≈ 49,000 token / 96 秒** —— 加载 skill 正文 + `PLAN.md` + `STATUS.md` + 两个提交的 diff |

> ⭐ **用后面那个数做预算。** 7,300 是"什么都没干"的价格，不是审核的价格 ——
> 两者差了近 7 倍。第一次估的时候我用了前者，是错的。

⇒ 所以契约建议的预算规则是：**每个任务最多 1 轮 review + 1 轮复验；`P3` 不阻塞。**

### 档位会影响审核质量

同一个缺陷，在强档被报成 `P1`，在便宜档被报成 `P2` 并拆得更细。

⇒ **审核用哪一档，是个要你显式决定的事**，别让它跟着默认值走。

## 五、契约里几个不显然的规定

### 验收标准分三级

`[命令]` / `[观察]` / `[现场]`。

前两级工人能自证，**第三级不能** —— 它需要人站在现场。

设 `[现场]` 这一级的价值不是"让不可自动化的东西自动化"，是**把它压到最短**：
强制写清"谁 / 在哪 / 做什么 / 什么算通过"，于是那几秒现场时间不需要现想。

### `UNVERIFIED ≠ DONE`

任务状态有五个词，其中 `UNVERIFIED`（可自动的全过、现场还没验）**不等于** `DONE`。

这条是**专门用来杀静默失败**的：那种"报告成功但实际什么都没做"的失败。它是最难发现的一类
缺陷，因为它长得和成功一模一样。

放宽这一条，整个契约就退化成"agent 说完成就完成"。

### 验收标准是契约，不是草稿

改了它 = 移动靶 ⇒ 该任务**重新声明为未完成**，且必须在 `PLAN.md` 里留痕。

## 六、已知的取舍

| 取舍 | 代价 |
|---|---|
| 文件交接而非实时 | 同步有延迟 —— 要到下一个回合边界 |
| 人闸 | 需要你在关键点出现 |
| 非对称分工（领导固定为 Codex） | 不能反过来让 Claude Code 当领导 |
| 零依赖（纯 skill 文件夹） | 没有自动更新通道 |
