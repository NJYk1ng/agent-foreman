# 契约规范

两个 agent 不共享会话。**这份契约是它们唯一的接口。**

任何一方偏离它，协作就退化成靠猜 —— 而靠猜正是本项目要消灭的东西。

读这份文档的人：`agent-contract`（两端都装）、`tech-lead`、`cross-review`、`execute-plan`。
改了这里，四个 skill 都要跟着改。

---

## 一、目录

```
<项目根>/.foreman/
├── PLAN.md       当前计划          —— 领导写
├── STATUS.md     工人的汇报        —— 工人写
├── BLOCKED.md    工人的求助        —— 工人写
├── REVIEW.md     领导的审核结论    —— 领导写
└── archive/      已归档的旧计划
```

**规则**

1. 放在**项目根**，**提交进 git**。它是审计线索，不是缓存。
2. 同一时刻只有**一份** `PLAN.md`。开新计划时，把旧的 `PLAN.md` / `STATUS.md` / `REVIEW.md`
   一起移到 `.foreman/archive/<YYYY-MM-DD>-<slug>/`。
3. 一个 `.foreman/` 对应一个工作单元（一个 PR 的量级）。**计划做完了就归档**，别让文件无限长大。

---

## 二、`PLAN.md`

```markdown
# PLAN — <一句话标题>

> 领导：<会话标识> · <日期> · 来源：<需求从哪来>

## 背景与约束

（为什么做、不能碰什么。3~6 行。这一段是给工人省上下文用的 —— 写清它就不用来回问了。）

## 任务

### T1 <标题>

- **目标**：一句话，必须能判断"达成没达成"
- **谁写**：CC | Codex
- **依赖**：无 | T0, T2
- **验收标准**：
  - AC1 [命令] `<命令>` → <期望输出>
  - AC2 [观察] <观察什么> → <期望>
  - AC3 [现场] <谁> / <在哪> / <做什么> → <什么算通过>
- **边界**：不许改 <文件 / 行为>

### T2 <标题>
...
```

### 字段规则

| 字段 | 必填 | 规则 |
|---|---|---|
| **目标** | ✅ | 必须能回答"达成没达成"。写不出可判断的目标 = 这条任务还没想清楚 |
| **谁写** | ✅ | `Codex` = 领导**亲自写**。留给最难的那 10%（见下） |
| **依赖** | ✅ | 没有就写 `无` |
| **验收标准** | ✅ | 至少 1 条 |
| **边界** | ✅ | 没有写 `无` —— 但写 `无` 之前想一下 |

### ⭐ `谁写：Codex` 什么时候用

留给满足**任意一条**的子任务：

- 涉及**坐标系 / 时态 / 并发**这类"写错了测试也测不出来、现场才暴露"的地方
- 是**核心算法**，而不是围绕它的脚手架
- 领导自己**没把握** —— 那说明它就该自己上手验证

理由：一行都不碰的领导，等于把最难的部分交给最弱的模型，而系统恰好崩在那里。

## 三、验收标准（本规范的核心）

每条验收标准的格式：

```
AC<n> [级别] <做什么> → <什么算通过>
```

### 三个级别

| 级别 | 定义 | 谁来证 | 能自动吗 |
|---|---|---|---|
| `[命令]` | 一条命令 + 期望输出 | 工人自己跑 | ✅ |
| `[观察]` | 一个可观察的事实 + 怎么观察 | 工人自己跑 | ✅ 多半能 |
| `[现场]` | 需要人 / 实物在场 | **人** | ❌ |

```markdown
  - AC1 [命令] `pytest tests/test_nav.py::test_retry` → 12 passed
  - AC2 [观察] `rostopic hz /slam_odom` 持续 30s，频率 ≥ 10Hz
  - AC3 [现场] 人 / 工位 / 摆好机器人后点一次【重定位】 → 单次成功，不再需要连点
```

### 硬规则

1. **必须可证伪。**
   ❌「导航稳定」 → ✅「连续 5 次导航到 A 点，5 次都成功」
2. **不许自我评价。**
   ❌「代码看起来对」「逻辑清晰」「已优化」—— 那是感想，不是验收。
3. **`[现场]` 必须写全四件事**：谁 / 在哪 / 做什么 / 什么算通过。
   ⭐ 目的是**把"现场那几秒"压到最短**。这才是这套东西真正的价值 ——
   不是消灭不可自动化的部分，是让它尽量小。
4. **`[现场]` 工人不许判通过**（见第四节的 `UNVERIFIED`）。
5. 验收标准**必须能被检查者独立复现**。领导审的时候会自己再跑一遍 `[命令]` 和 `[观察]`。

## 四、`STATUS.md`

```markdown
# STATUS — <对应 PLAN 的标题>

> 工人：<模型> · <日期> · 提交：<sha>

## T1 <标题> —— 状态：DONE

- **AC1 [命令]**: ✅
  ```
  <贴真实输出，不许复述>
  ```
- **AC2 [观察]**: ✅ 实测 32.1Hz（持续 45s）
- **AC3 [现场]**: ⏳ 待现场验证 —— 容器里没有机器人
  - 复现步骤：
    1. 把机器人摆到工位起始位姿
    2. 面板 → 点【重定位】一次（**不要连点**）
    3. 看：面板显示配准成功；`rostopic hz /slam_odom` 不掉
  - 判据：单次点击即成功 = 通过
- **改动**：`nav_goto.py:120-148`、`ros_bridge.py:88`
```

### ⭐ `[观察]` 的证据要**可独立核对**

不要写「我读过了，没问题」「确认已实现」—— 那是**结论**，领导没法验，只能自己重做一遍，
那这次汇报就白写了。

要写**能 grep 到的东西**：

```markdown
- **AC2 [观察]**: ✅ `grep -n 'retry exhausted' logs/nav.log` ⇒ `142:retry exhausted after 3 attempts`
- **AC3 [观察]**: ✅ `grep -n '用文件交接' docs/architecture.md` ⇒ `28:## 二、⭐ 为什么用文件交接，不用实时通信`
```

原则：**把"我怎么知道的"变成"领导也能跑一遍的东西"。**

> 📌 这条是跑闭环跑出来的：第一次汇报时我们写的是「人工通读确认，见第二节」，
> 被领导 `BLOCK` —— 因为它无法在不重读全文的前提下核对。章节指针**不是**证据。

### ⭐ 任务状态：五个词

| 状态 | 含义 |
|---|---|
| `TODO` | 领导已规划，工人未开始 |
| `WIP` | 工人在做 |
| `BLOCKED` | 卡住，求助已写进 `BLOCKED.md` |
| `UNVERIFIED` | 可自动的 AC 全过，但还有 `[现场]` 没验 |
| `DONE` | **全部** AC 有结论**且都通过** |

> ⭐⭐ **`UNVERIFIED` ≠ `DONE`。这是本规范最重要的一条。**
>
> "报告成功但什么都没做"这类**静默失败**，就死在这一条上。
> 工人不许因为"我觉得没问题"把 `UNVERIFIED` 写成 `DONE`；也不许因为
> "现场那条肯定没问题"直接跳过。

## 五、`BLOCKED.md`

```markdown
# BLOCKED — T1

- **卡在哪**：一句话
- **已试过**：（列出来）
- **需要决定的**：一个具体问题
- **相关代码 / 日志**：（最小片段）
```

⭐「**已试过**」这一节是**省额度**的关键：没有它，领导会把工人已经排除的路再建议一遍，
白白花掉一轮额度。

一个任务同时只能有一个活跃的 `BLOCKED.md`。解决了就删掉（结论记进 `STATUS.md`）。

## 六、`REVIEW.md`

```markdown
# REVIEW — <审核对象>

> 领导：<会话标识> · <日期> · 对象：<sha / diff 范围>

## 结论：BLOCK | PASS

### [P1] <一句话标题> —— `path/to/file.py:123`

<一段话：什么样的场景会走到这里、为什么会错、作者知道了会不会改>

## 对照验收标准

- T1/AC1 `[命令]` ✅ 已独立复现
- T1/AC2 `[观察]` ✅ 输出与我独立跑的一致
- T1/AC3 `[现场]` ⏸ 无法判定 —— 步骤已写清，现场验证后回填
```

### 分级

| 级别 | 含义 |
|---|---|
| `P0` | 发布阻断 / 严重故障 |
| `P1` | 紧急缺陷，下一步就该修 |
| `P2` | 普通缺陷 |
| `P3` | 影响低，但值得修 |

### 报告纪律

- **只报本次改动引入的问题**，不报既有问题（既有问题另开一条记录）。
- **每条都要能演示**：什么样的输入/操作会走到这里。演示不出来 = 推测，不许报。
- **风格挑剔不进正文**（风格不阻塞）。
- **没找到就写「无发现」。不许为了凑数编一条。**
- ⭐ **`[现场]` 那几条领导不能判通过** —— 只能判"复现步骤写没写清"。

## 七、写入权限

| 文件 | 只能写 | 谁可以读 |
|---|---|---|
| `PLAN.md` | 领导 | 双方 |
| `REVIEW.md` | 领导 | 双方 |
| `STATUS.md` | 工人 | 双方 |
| `BLOCKED.md` | 工人 | 双方 |

- 工人**不许**改 `PLAN.md`。觉得计划有问题 → 写 `BLOCKED.md`。
- 领导**不许**改 `STATUS.md`。觉得汇报有问题 → 写 `REVIEW.md`。

---

## 八、变更规则

**验收标准是契约。改它 = 移动靶。**

1. 改之前必须在 `PLAN.md` 里留痕：
   `⚠️ AC2 变更于 2026-10-16：<原因>`
2. 已经派发出去的任务，改了验收标准 ⇒ **该任务重新声明为未完成**。
3. 新加任务只能**追加**，不许重排既有编号（`T3` 永远是 `T3`）。

---

## 九、额度纪律的接口

领导的额度是**硬上限**。下面三件事花钱，**必须经过人**：

| 动作 | skill | 触发方式 |
|---|---|---|
| 出计划 | `tech-lead` | 人显式发起 |
| 审代码 | `cross-review` | 人显式发起 |
| 应答阻塞 | — | 人显式发起 |

⭐ **工人侧不许自动触发这三件事中的任何一件。**
钩子（期二）可以在回合边界**把消息浮出来**，但**花额度的那一步永远留一道人闸**。

> 这不是"没做完"，是**刻意设计**：额度烧光时流程会停在任务做到一半的地方，
> 而在额度受限的场景里，一个"停下来问"的设计比一个"全自动"的设计更可靠。

### ⭐ 人闸还要求**可见性**

**光"经过人"不够 —— 动作必须是看得见的。**

如果工人能悄悄把领导的额度花掉，人只看到一个结果、看不到过程，那这道闸门就是假的：
人没法判断"这次花得值不值"，也没法在跑偏时叫停。

| 要求 | 反面 |
|---|---|
| ✅ 输出打在**人能实时看到的窗口**里 | ❌ 输出进管道，人只看到被转述的一句 |
| ✅ 推理摘要开着（`model_reasoning_summary`） | ❌ 人只看到结论，看不到它怎么得出结论 |
| ✅ 全程可中断 | ❌ 跑完才知道发生了什么 |

> 📌 这条是实测出来的：工具的初始形态是把 Codex 的输出 capture 进调用方的管道 ——
> 结果是人看不到思考过程，只看到一个被 `tail` 截断的结尾。
> 修法是让调用方**在一个可见的终端窗口里**跑它，同时 tee 一份日志给自己读：
> 两边都拿到，而且人都看得见。

## 十、反例

不合格的契约长这样：

```markdown
### T1 优化导航
- 目标：让导航更稳定
- 验收标准：测试通过
```

三个错误：**目标不可判断**（"更稳定"是相对的）、**验收标准没有命令也没有观察事实**（"测试"指哪个？）、
**没有边界**（工人不知道该在哪停手）。

同一个任务的合格版本：

```markdown
### T1 导航重试
- **目标**：目标点被占据时，重试 3 次后返回 Err，而不是无限等待
- **谁写**：CC
- **依赖**：无
- **验收标准**：
  - AC1 [命令] `pytest tests/test_nav_retry.py` → 6 passed
  - AC2 [观察] 日志在放弃时出现 `retry exhausted`，且总共只有 3 次尝试
  - AC3 [现场] 人 / 工位 / 手动把 A 点用障碍物占住后下发导航 → 60s 内返回失败，机器人不动
- **边界**：不许改 `duration=1` 的失联刹车逻辑
```
